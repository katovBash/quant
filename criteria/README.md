# Критерии проверки стратегии

## Из эксперимента в стратегию-кандидат

Для ручной проверки Pine допустим промежуточный статус `TV_REVIEW`: скрипт проверяет исторический фильтр и ручные отметки, но позволяет оставить `costs_checked=false`, если часть расходов ещё неизвестна. В этом статусе Python и Pine уже лежат рядом, но автоматический paper trading не подключён. После сверки в TradingView отдельно решаем, переходить ли к бумажному исполнению; неизвестную стоимость short и расхождения сделок нельзя скрывать отметкой `costs_checked=true`.

Папку в `strategies/` создаём для **одного выбранного правила и явной области применения**, когда в эксперименте сохранены полный перебор и источник свечей, а для выбранной пары «тикер × интервал» выполнен исторический фильтр ниже. Область может быть `single_ticker`, `basket` или `universal`; последнее слово не означает гарантированную прибыль на каждой акции. До переноса фиксируем параметры EMA/других индикаторов, направление, вход, выход, размер позиции, издержки, контроль и дату решения; ссылка на эксперимент остаётся в README стратегии. Отдельно проверяем, что результат не является одиночным пиком среди соседних параметров и что поздний период не использовали повторно для подбора. Для `basket` и `universal` ту же пару без перенастройки проверяем на всей заявленной области по [шаблону](../experiments/template/README.md), сохраняя также убытки и отсутствие данных. Для `single_ticker` прибыль других бумаг не требуется; последующие независимые данные по самому тикеру особенно важны. Если другие бумаги или поздний период уже просматривали, явно маркируем проверку как `seen_history`.

Для автоматизации перехода создайте в эксперименте `candidate.json` по [примеру](../experiments/template/candidate.example.json), укажите путь к полной CSV-таблице и точный селектор строки, приложите Pine- и Python-файлы и задокументируйте ручные проверки. Затем из корня запустите `python3 -m criteria.promote_experiment experiments/<папка>` для сухой проверки и ту же команду с `--apply` для копирования выбранного кода. Скрипт не выбирает автоматически топ‑5 и не принимает произвольный порог доходности: прибыльный максимум после тысяч попыток может быть случайным. Он проверяет численный фильтр, наличие исходных файлов и обязательных отметок обзора; истинность ручных отметок и совпадение Pine-сделок с Python **не может проверить сам**. Текущий EMA12/33 был перенесён до появления скрипта и отдельно отмечен как кандидат на просмотренной истории. Перенос не запускает paper trading.

Для скрипта нужна исходная строка с колонками полного и позднего периода, например CSV нового EMA-перебора. Сводные `results.csv` в `experiments/.history/rule-reviews` не содержат поздних метрик и сами по себе не подходят для автоматического переноса: сначала нужен сопоставимый расчёт на двух периодах. Флаги ручного обзора в `candidate.json` — запись ответственности исследователя, а не автоматически доказанный факт. Для `basket` и `universal` отметка `cross_ticker_checked=true` обязательна: приложите заполненный [отчёт переноса](../experiments/template/cross_ticker_validation.csv), включая проигравших, и отметьте `seen_history` либо `unseen_holdout`. Для `single_ticker` эта отметка не требуется. Скрипт не проверяет полноту отчёта самостоятельно. При отрицательном переносе сузьте область до тех бумаг, для которых зафиксировали отдельную гипотезу, и проверьте её на новых данных.

Это **кандидат на проверку**, а не подтверждённая стратегия. Прежние 20 прототипов и отчёты по всем 21 правилам уже перенесены в [эксперименты](../experiments/.history/rule-reviews/README.md). Актуальный список правил и статусов находится в [каталоге стратегий](../strategies/README.md): EMA12/33 остаётся действующим бумажным пилотом, остальные варианты предназначены для ручной сверки. Новые кандидаты RSI, ADX, уровней и пробоя добавлены для этой сверки напрямую и **не имеют отметки о прохождении автоматического скрипта переноса**; их численные результаты и ограничения перечислены в README. Pine и Python-сигнал сверяются по сделкам перед автоматизацией; наличие Python-файла само по себе не включает бумажный сервис.

**Число сделок зависит от таймфрейма и редкости сигнала.** Фиксированный порог 100 сделок снят с исторического допуска. Для ручного разбора требуются положительная общая и поздняя доходность после базовых издержек, profit factor >1,2, просадка не глубже 20% и помесячная таблица; число сделок в каждом месяце показывается как мера информативности. Для комбинации сравниваем чистую EMA в раннем и позднем периодах. Это только исторический фильтр: лучший тикер уже выбран после просмотра данных.

Перед созданием стратегии-кандидата `monthly_report` в `candidate.json` указывает помесячный отчёт по выбранной паре. Скрипт требует хотя бы два разных полных месяца с PnL и числом сделок и записывает долю прибыльных месяцев и худший месяц в `robustness.json`. Отдельный убыточный месяц не блокирует кандидата, но общий численный порог доли прибыльных месяцев и допустимого убытка следует фиксировать до просмотра результатов; пока он не согласован, статус остаётся исследовательским. `trade_window_report` можно приложить дополнительно, если хватает сделок.

Перед допуском отдельно смотрим риск начала в неудачный момент: дневную кривую капитала, 7- и 14-дневные окна с еженедельным стартом, каждый календарный месяц с числом сделок, все доступные старты по месяцам на горизонтах 6/12/24 месяца, худшее окно и максимальную длительность ниже предыдущего пика. Короткие окна без закрытых сделок отдельно помечаем как малоинформативные. Сравнение ведём на тех же датах с заранее выбранным контролем. Это диагностическая проверка сверх численного фильтра, а не автоматическое доказательство преимущества: перекрывающиеся окна зависимы, а выбранные настройки уже подогнаны к истории. Если худшее окно или длительность неприемлемы для заранее установленного бюджета риска, кандидат не получает разрешения на реальные деньги независимо от общей доходности. Размер позиции и совокупный риск по коррелированным виртуальным счетам оцениваем отдельно.

Для **операционного решения по paper trading** применяем выбранный владельцем проекта короткий цикл: после 30 календарных дней с даты запуска, если виртуальный капитал вырос относительно начального **после подтверждённых расходов**, счёт получает категорию `APPROVED_30D_PAPER`. При нулевой или отрицательной доходности — `NOT_APPROVED_30D`; если расходы, включая short, не подтверждены — `COSTS_UNVERIFIED`. До 30 дней категория `OBSERVING`. Это одобрение **только для продолжения виртуальной проверки**, не для реальных денег и не доказательство устойчивого преимущества. При изменении правила, тикера или интервала начинаем новый счёт и отсчёт.

Отдельный, более строгий статус **свидетельства преимущества на новых данных** пока требует минимум 100 новых закрытых сделок и 252 торговых дня после фиксации кода, превосходства заранее выбранного контроля после подтверждённых расходов и теста неопределённости. Этот исследовательский порог **не задерживает** месячное операционное решение. Если позже пересмотрим его, зафиксируем новый протокол до просмотра новых результатов. Число сделок само по себе не доказывает устойчивость: сделки одного тренда зависимы.

## Статусы

| Статус | Значение |
| --- | --- |
| `UNTESTED` | Есть идея или Pine, нет сопоставимого расчёта сделок. |
| `HISTORICAL_CANDIDATE` | Хороший результат найден на уже просмотренной истории. Это статус всех нынешних кандидатов. |
| `OBSERVING` | Виртуальному счёту ещё нет 30 календарных дней. |
| `APPROVED_30D_PAPER` | После 30 дней виртуальный капитал вырос относительно начального, расходы подтверждены; одобрено только продолжение paper trading. |
| `NOT_APPROVED_30D` | После 30 дней виртуальная доходность неположительна. |
| `COSTS_UNVERIFIED` | Месяц прошёл, но расходы не подтверждены; одобрения нет. |
| `INSUFFICIENT_EVIDENCE` | Новых закрытых сделок меньше 100, торговых дней меньше 252 или расходы не подтверждены. |
| `NO_RELIABLE_EDGE_DETECTED` | На новых данных не выполнены критерии преимущества, риска или статистического теста. Это не доказательство отсутствия любого возможного преимущества. |
| `FORWARD_EVIDENCE_OF_EDGE` | Фиксированное правило после расходов обогнало контроль, просадка не превысила лимит и односторонний блочный bootstrap дал скорректированное значение ниже 0,05. Это свидетельство, а не гарантия будущей прибыли. |

## Входные файлы

`equity.csv` — ежедневная стоимость **одинакового начального капитала** для стратегии и контроля после всех расходов:

```csv
date,strategy_equity,baseline_equity
```

`closed_trades.csv` — по одной строке на каждую реально закрытую сделку после фиксации:

```csv
exit_date
```

Для фильтра EMA контроль — чистая EMA12/33 на тех же свечах, размере и расходах. Для чистой EMA заранее выбирается удержание той же доли акции либо денежный счёт; выбор контроля после просмотра результата запрещён. При short в расходах нужны заём бумаги и выплаты по дивидендам.

## Запуск

Исторический допуск к бумажной проверке, например для EMA12/33 long+short на 1H:

```bash
python3 criteria/screen_historical.py \
  --input experiments/.history/legacy-ema/12-33-cross/execute/research/intraday/all_results.csv \
  --timeframe 1H --fast 12 --slow 33 --mode long_short
```

Проверка по **новым** бумажным сделкам:

```bash
python3 criteria/evaluate.py \
  --equity papertrading/equity.csv \
  --trades papertrading/closed_trades.csv \
  --frozen-on 2026-11-01 \
  --paper-started 2026-11-01 --paper-initial-capital 1000000 \
  --tested-variants 1 \
  --costs-verified --has-short --short-costs-verified
```

В выводе `paper_status` — месячная категория, а `status` — отдельная исследовательская оценка преимущества. Сводку по всем виртуальным счетам создаёт `python3 -m papertrading.status`, её читабельная версия находится в [статусах paper trading](../papertrading/live/STATUS.md). Оценщик не может сам подтвердить тарифы: отметки в `review.json` выставляются только после ручной проверки расходов.

`--tested-variants` — число вариантов, **просмотренных на том же новом периоде**; скрипт применяет консервативную поправку Бонферрони. Значение `p` — приблизительная вероятность получить не менее сильное среднее превышение при гипотезе отсутствия преимущества. **Это не вероятность того, что стратегия случайна.** Блочный bootstrap сохраняет часть временной зависимости, но качество вывода зависит от выбора длины блока, режима рынка и достоверности входных данных.

Скрипт не может проверить сам факт предварительной фиксации кода и полноту брокерских расходов. Их нужно записать в README бумажного эксперимента и сверить по сделкам. [Подробный протокол](PAPER_VALIDATION.md). Исторический перебор и множественные проверки обсуждаются в [White, *A Reality Check for Data Snooping*](https://doi.org/10.1111/1468-0262.00152) и [Bailey et al., *The Probability of Backtest Overfitting*](https://escholarship.org/uc/item/4w1110bb).
